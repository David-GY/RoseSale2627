Rose Sale Shift Scheduler: Design Doc

Status: Draft for review · Approach: B (separate web app + Google Sheets API) · Date: 2026-11-09

NOTE

All names, IDs, committees, roles, dates and slot times in this doc are placeholders. Everything event-specific is read from the sheet's Config and Roster tabs at runtime, so swapping in real data needs no code changes.

1. Goal

Replace hand-filled shift tabs (FEB 9 Shifts … FEB 14 Shifts) with:

A when2meet-style web app. A core member enters their ID number, drags across a grid to mark availability, and ranks their preferred roles.
An auto-assigner that builds the best schedule it can, given availability, committee eligibility, headcount needs and fairness.
Write-back of the schedule into the Google Sheet in the existing format ([COMMITTEE] First Last per cell), where admins can still edit by hand.
Non-goals (v1)
Shift swapping or trading between members
Notifications (email/Discord) when the schedule is published
Multiple concurrent events (the data model allows it; see §11)
2. Architecture
Layer	Choice	Why
Framework	Next.js (App Router) + TypeScript	One repo for UI + API routes; free Vercel hosting
UI	Tailwind + a custom drag-select grid component	when2meet-style UX, works on mobile with touch
Validation	zod	One schema shared by the client, the API and sheet parsing
Sheets access	googleapis with a service account	No per-user OAuth; the sheet is shared with the service account email
Optimizer	highs (HiGHS solver compiled to WASM)	Real MILP solver that runs in a serverless function; handles this problem size in well under a second
Admin auth	Passcode in an env var (v1) → Google sign-in allow-list (v2)	Starts simple and is easy to upgrade

Key boundary: all sheet reads and writes go through a single SheetRepository interface (§6). If you later move to a database (approach C), you only replace this module.

4. Web App: Pages & UX
4.1 / Member flow

Availability grid

Columns = dates, rows = slots (from Cfg_Slots). On mobile it switches to one day at a time with swipe tabs.
Click and drag (mouse) or long-press then drag (touch) to toggle a range, as in when2meet.
Pre-filled with previous answers if the member has already submitted.
A small "group heat" overlay (number of people already available) can be turned on in Settings. Off by default.

Role ranking

Shows only the roles the member's committee is allowed to do, with their labels and icons.
Pick 1st/2nd/3rd from dropdowns or a drag list. At least 1 is required and 3 is the maximum. The UI says these are preferences: "you may be placed in any role your committee is eligible for."
4.2 /admin (passcode-protected)
Panel	Purpose
Responses	Who has and hasn't submitted (compared against active Roster), with a "copy missing names" button
Heatmap	Slot × role grid showing how many eligible, available people there are vs MinPerSlot. Red cells = guaranteed shortfall before running the optimizer
Run auto-assign	Runs the optimizer and shows a preview (same layout as the sheet) plus stats: coverage %, % who got their 1st choice, min/avg/max shifts per person
Publish to sheet	Writes Assignments, Unfilled, and re-renders the FEB X Shifts tabs
Settings	Form open/close toggle, re-read Config button (clears the cache)

IMPORTANT

Run and Publish are separate steps on purpose. Admins can re-run with different weights and compare results before anything in the sheet is overwritten.

Because the default W_Coverage is much larger than any preference weight, filling a slot always beats giving someone their top choice. Fairness then breaks ties between equally good fills. All weights can be changed in Cfg_Settings.

NOTE

Coverage is a weighted soft constraint, not a hard rule. If a slot cannot be filled with available, eligible people, the solver still returns a schedule and reports the gap in Unfilled instead of failing.

5.3 Size & performance

Placeholder scale: ~80 people × 6 days × 8 slots × 9 roles is about 35k raw combinations. After filtering by availability and eligibility, typically under 8k variables, which HiGHS solves in well under a second. A 20 s time limit plus a "best found so far" fallback protects against Vercel's function timeout.

Fallback: if the solver fails or times out, a deterministic greedy pass fills the scarcest slot × role first (fewest eligible available people), choosing the person with the highest preference score and fewest shifts so far. The result is marked "heuristic" in the admin preview.

5.4 Admin pins & re-runs
An admin can lock a cell in the preview. It's saved as Locked=TRUE in Assignments.
Re-runs keep locked rows and re-optimize everything else, so manual tweaks survive a late submission.
Edits made directly in the FEB X Shifts tabs are not read back in v1 (the tabs are only a view). The admin UI warns about this before publishing. Reading hand edits back in is Phase 4.
5.5 Determinism

People and slots are sorted by ID/SlotId before the model is built, so the same inputs always give the same schedule.

SheetRepository interface

ts
interface SheetRepository {
  getConfig(): Promise<EventConfig>;            // settings, committees, roles, slots, overrides
  getRoster(): Promise<Person[]>;
  getResponses(): Promise<Response[]>;
  upsertResponse(r: Response): Promise<void>;
  getAssignments(): Promise<Assignment[]>;      // incl. locked
  writeAssignments(run: AssignmentRun): Promise<void>;
  writeUnfilled(rows: UnfilledRow[]): Promise<void>;
  renderShiftTabs(run: AssignmentRun, cfg: EventConfig): Promise<void>;
}

The optimizer and writer are pure functions ((inputs) => outputs) with no I/O, so they can be fully unit-tested.

7. Sheet Write-Back (FEB X Shifts tabs)

The existing tabs have a fixed visual layout: role columns C–K, several rows per slot, merged time cells in column B. To fill them correctly, the writer needs to know where each slot block starts.

Layout mapping: add 2 columns to Cfg_Slots:

…	Tab	StartRow	RowCount
…	FEB 10 Shifts	13	4

The writer then, for each slot:

Clears SheetColumn{StartRow}:{StartRow+RowCount-1} for every role column (values only, so colours, borders and merges stay).
Writes the assigned people top to bottom as [COMMITTEE] First Last, sorted by committee then name.
If assignments exceed RowCount, it puts the extra names in the last cell separated by line breaks and logs a warning in Unfilled.

All writes are batched into one spreadsheets.values.batchUpdate call per publish to stay within API quotas.

TIP

Alternative for later: have the writer generate each day tab from a template tab (_Template Shifts) instead of writing into hand-built ones. Then adding a day = adding rows in Cfg_Slots. Phase 4.

Concurrency on Responses:

Upsert = read the ID column → find the row → values.update the row, or values.append if the person is new.
A short in-function retry plus a SubmittedAt compare-and-set guards against two submissions at the same moment. That's enough for roughly 100 members. If it ever isn't, move responses to a database (§11).
8. Identity, Security & Privacy
Risk	Mitigation
Someone enters another member's ID	VerifyField setting: LAST_NAME (case-insensitive) or PIN (a PIN column in Roster). Default is NONE while you're on placeholders; turn it on before the real launch
ID enumeration	Rate-limit /api/member/[id] per IP. The lookup only returns first name + committee until verification passes
Admin access	ADMIN_PASSCODE env var → signed httpOnly cookie. Upgrade path: Google sign-in with an email allow-list
Service account key leak	Key kept only in Vercel env vars, never sent to the client. The service account has Editor access to this one sheet only
Editing after the deadline	FormOpen=FALSE makes the API reject writes, not just hide the UI
Privacy	No public view of other members' availability. The heat overlay shows counts only
9. Edge Cases
Case	Behaviour
ID not found / inactive	"ID not found, contact your PM" message; nothing is created
Member's committee isn't eligible for any role	Shown "No roles available for [COMMITTEE]". Can still submit availability (helps the admin see who's free)
Member selects zero slots	Allowed (counts as "not available"). Excluded from the fairness bounds
Config edited after responses exist	Responses that mention deleted SlotIds are ignored with a warning in the admin view; new slots show as "no data yet"
Committee code typo in Roster/Roles	Config validation on load lists the bad rows in the admin dashboard; the optimizer won't run until they're fixed
Role with Min > Max, or overrides referencing an unknown slot	Same: validation error, no run
Total demand > total supply	Solver still returns a schedule; shortfalls go to Unfilled and the heatmap
10. Testing
Unit: buildModel (eligibility/availability filtering, caps, locks), the greedy fallback, ScheduleWriter cell layout, zod parsing of each Config tab including the bad-data cases above.
Property tests: for random small instances, check that every assignment is available, eligible, within capacity and one-per-slot, and that results are deterministic.
Integration: InMemoryRepository seeded with placeholder Roster/Config, running the full member submit → assign → publish flow.
Manual staging: a copy of the sheet shared with the service account; SHEET_ID env var points to the copy until launch.
11. Expandability (built for placeholders)
Future change	What you do
Real roster / roles / dates	Edit Roster and Cfg_* tabs. No code change
Add a role column	Add a row in Cfg_Roles + a column in the shift tabs
Different slot lengths per day	Edit Cfg_Slots rows
New fairness / preference rules	Add a weight key in Cfg_Settings + one term in buildModel
Multiple events (e.g. Rose Sale + another)	Add an EventId column / one sheet per event, selected via the ?event= URL param → SHEET_ID lookup
Outgrow Sheets (concurrency, history)	Implement SupabaseRepository or ConvexRepository. Keep the sheet as an export by calling only renderShiftTabs
Notify members	After publish, read Assignments → send email or Discord messages (Phase 4)
